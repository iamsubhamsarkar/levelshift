
## BUILD_STEP
goal: Create service.py that exposes ATLAS behind an endpoint, with guardrails at the boundary.
why: The agent sits inside an ordinary service, with input and output guardrails guarding the entrance and exit — structurally identical to a validating web controller. (Learned in Phase 9, Ch 17, section 17.2.)
code:
```
# service.py
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel
from atlas import guarded_run

app = FastAPI(title="ATLAS")

class Query(BaseModel):
    goal: str

@app.post("/ask")
def ask_endpoint(q: Query):
    try:
        answer, trace = guarded_run(q.goal)   # guardrails run inside guarded_run
        return {"answer": answer, "trace_id": trace.trace_id, "steps": trace.summary()["steps"]}
    except ValueError as e:
        raise HTTPException(status_code=400, detail=str(e))  # blocked by input guardrail
```
verify: service.py saves. The endpoint validates input (via the guardrail), runs the agent, and returns the answer plus a trace id — a clean request-in, answer-out contract.
reference: Phase 9, Ch 17

## BUILD_STEP
goal: Run the service and call it.
why: This turns ATLAS from a script into a service others can call over HTTP. (Learned in Phase 9, Ch 17, section 17.1.)
windows:
```
uvicorn service:app --reload --port 8000
```
ubuntu:
```
uvicorn service:app --reload --port 8000
```
verify: The server starts on port 8000. Open http://localhost:8000/docs in your browser and use the interactive form to POST a goal to /ask — you get back an answer and a trace id.
troubleshoot: Note: a dangerous-tool approval prompt (Unit 4) blocks on console input, which does not fit a web request. For the service, either exclude dangerous tools or replace the console prompt with a "pending approval" response — see the next step.
reference: Phase 9, Ch 17

## BUILD_STEP
goal: Make the service STATELESS — store conversation state outside, keyed by session id.
why: A stateless service can run as many copies as you need; conversation memory lives in an external store keyed by session. (Learned in Phase 9, Ch 17, section 17.2.)
code:
```
# Keep sessions in an external dict (a real system uses a database/redis):
SESSIONS = {}   # session_id -> messages list

class Query(BaseModel):
    goal: str
    session_id: str | None = None
# Load/create the session's messages by session_id, run the agent, save it back.
# The service process itself holds no per-user state in module globals.
```
verify: Two different session_ids maintain separate conversations; restarting the service does not lose state IF you persist SESSIONS to disk or a store. The service instance holds no request-specific state of its own.
reference: Phase 9, Ch 17

## BUILD_STEP
goal: Handle the dangerous-action gate in a web-appropriate way.
why: A web request cannot block on console input; instead, return a "needs approval" response and require a second, explicit confirm call. (Learned in Phase 9, Ch 16-17.)
code:
```
# If the agent wants a dangerous tool, DON'T prompt on the console.
# Instead return: {"status": "needs_approval", "action": {...}, "token": "..."}
# The caller reviews it and POSTs to /approve with the token to actually run it.
# This is human-in-the-loop adapted to an async, multi-user service.
```
verify: When ATLAS proposes a dangerous action over the API, the response says "needs_approval" with the proposed action, rather than silently running it or hanging. Approval happens via a separate, explicit call.
reference: Phase 9, Ch 16, Ch 17
