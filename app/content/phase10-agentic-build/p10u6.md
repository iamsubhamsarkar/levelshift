## BUILD_STEP
goal: Add a tool that can fail, and make it fail on purpose.
why: The most-skipped competency is error handling. We will deliberately break a tool, then make ATLAS recover — errors as observations. (Learned in Phase 9, Ch 7, section 7.3.)
code:
```
def fetch_fact(topic: str) -> dict:
    """Look up a fact about a topic. (Simulated: fails for 'unknown'.)"""
    known = {"python": "Python was released in 1991.",
             "http": "HTTP is a stateless request-response protocol."}
    if topic.lower() not in known:
        return {"error": f"no fact found for '{topic}' — ask the user to pick a known topic"}
    return {"fact": known[topic.lower()]}

TOOL_IMPLS["fetch_fact"] = fetch_fact
TOOLS.append({
    "type": "function",
    "function": {
        "name": "fetch_fact",
        "description": "Look up a fact about a topic. Known topics: python, http. "
                       "Returns an error for unknown topics.",
        "parameters": {
            "type": "object",
            "properties": {"topic": {"type": "string", "description": "Topic to look up."}},
            "required": ["topic"],
        },
    },
})
```
verify: The file saves. The tool returns a clear, informative error for unknown topics instead of crashing — exactly what the theory calls "informative failures."
reference: Phase 9, Ch 6-7

## BUILD_STEP
goal: Confirm the loop already feeds tool errors back as observations.
why: Because run_tool_call returns the error dict (rather than raising), your loop already hands it to the model as a tool result — the model SEES the failure and can adapt. (Learned in Phase 9, Ch 7, section 7.3.)
code:
```
# No new code needed IF your run_tool_call returns errors as data.
# Make sure tool exceptions become observations, not crashes:
def run_tool_call(tool_call):
    name = tool_call.function.name
    try:
        args = json.loads(tool_call.function.arguments)
        fn = TOOL_IMPLS.get(name)
        if fn is None:
            return {"error": f"unknown tool {name}"}
        return fn(**args)
    except Exception as e:
        return {"error": f"tool {name} raised: {e}"}
```
verify: The file saves. Any tool failure — bad arguments, an exception, an unknown topic — now returns as an {"error": ...} observation the model can react to.
reference: Phase 9, Ch 7

## BUILD_STEP
goal: Simulate a rate limit and add a simple retry-with-backoff around the model call.
why: Free tiers throttle you; robust code retries transient failures politely. This previews the reliability engineering of Ch 17. (Learned in Phase 9, Ch 3 and Ch 17.)
code:
```
import time

def ask_resilient(create_kwargs, retries=3):
    for attempt in range(retries):
        try:
            return client.chat.completions.create(**create_kwargs)
        except Exception as e:
            if attempt == retries - 1:
                raise
            wait = 2 ** attempt  # 1s, 2s, 4s
            print(f"[retry] {e} — waiting {wait}s")
            time.sleep(wait)
```
verify: When the provider returns a transient error (like a 429 rate limit), ATLAS waits and retries with growing backoff instead of failing immediately. On a healthy connection it succeeds on the first attempt.
troubleshoot: Only retry TRANSIENT errors (timeouts, 429, 5xx). Do not retry a 401 (bad key) or 400 (bad request) — those will never succeed and waste your quota.
reference: Phase 9, Ch 3, Ch 17
