## THEORY
heading: 5.0  The hinge of the whole book
body:
This short chapter carries one big idea, and it is a hinge for the whole book. So far the model produces PROSE — text meant for humans. To build software that ACTS on a model's output, you need the model to produce DATA in a predictable shape your code can rely on.

That capability — structured output — is the bridge from "a chatbot that talks" to "a component in a system." It is also, quite literally, the mechanism behind tool use (Chapter 6). Understand this well and the rest of agentic AI unlocks.
callout: Structured output is the bridge from "a chatbot that talks" to "a component in a system."

## THEORY
heading: 5.1  Why prose is not enough
body:
Consider a model classifying a bug report. Two possible outputs. Human-friendly (but useless to a program): "This looks pretty serious — I'd call it a major issue affecting login." Machine-friendly (something code can act on): severity = MAJOR, component = login, confidence = high.

The first is fine for a person to read but a nightmare for a program to use — your code would have to parse loose English to figure out the severity. The second is unambiguous: a program can immediately branch on it ("if severity is BLOCKER, alert the on-call engineer"). The moment a model's output takes a reliable, predictable shape, the model becomes a usable building block rather than a novelty.

In your world, this is the difference between a REST endpoint returning a blob of freeform text versus returning a well-defined JSON body that maps cleanly onto a Java object. You would never build a system on the former. Structured output is how we get the latter from an LLM.
callout: Predictable shape turns a model from a novelty into a usable building block.

## THEORY
heading: 5.2  What "structured output" means
body:
Structured output means asking the model to reply in a defined DATA FORMAT — overwhelmingly, in practice, JSON (the same key-value format you know from REST bodies). Instead of a paragraph, you get something like an object with named fields.
snippet:
{
  "severity": "MAJOR",
  "component": "login",
  "confidence": 0.8
}
snippetExplanation: What this shows: This is an object with three named fields. "severity" holds one of a fixed set of words; "component" holds a piece of text; "confidence" holds a number. Because the shape is predictable, code can read each field directly and act on it — no guessing, no parsing of loose sentences. It is exactly like a small data-transfer object arriving from an API. The goal, then, is not merely "get JSON," but "get JSON of the RIGHT SHAPE, every time." Achieving that reliably takes a little care, because a text-prediction machine will, left to itself, sometimes wrap the JSON in chatty text or bend the format.
callout: The goal is not "get JSON" — it is "get JSON of the RIGHT SHAPE, every time."

## THEORY
heading: 5.3  Three levels of reliability
body:
There are, roughly, three levels of rigor for getting good structured output. You need to understand the ladder, because it shows how a "usually works" trick becomes an "always works" guarantee.

LEVEL 1 — JUST ASK, IN THE PROMPT. You instruct the model: "Reply with only a JSON object with these fields, and no other text." This often works — but it is fragile. The model might still add a friendly preface, or wrap the JSON in code fences, and then your code has to clean up the mess. Fine for quick experiments; risky for real systems.

LEVEL 2 — ASK THE PROVIDER TO ENFORCE VALID JSON. Most providers offer a mode that FORCES the output to be syntactically valid JSON. This removes a whole category of problems: no stray prose, no broken syntax. However — and this is subtle but important — it guarantees the output is valid JSON, NOT that it has the fields and types you actually wanted. The model could still return the wrong keys.

LEVEL 3 — DEFINE A SCHEMA AND VALIDATE AGAINST IT. You define the exact expected SHAPE — which fields, of which types, within which ranges — and you check the model's output against that definition, rejecting anything that does not conform. This gives you output that is BOTH valid JSON AND the right structure. This is the professional default in 2026.

The Java parallel is precise: Level 3 is like receiving a JSON response, deserializing it into a typed object, AND running validation on it (the kind of field constraints you would express with validation annotations). You would never trust a raw external payload without validating it; you should not trust raw model output either. In Python this is commonly done with a library called Pydantic — but the concept, not the tool, is what matters.
callout: Level 3 — schema-defined and validated — is the professional default. Never trust raw model output.

## THEORY
heading: 5.4  Self-correction — a glimpse of something deeper
body:
A powerful pattern falls naturally out of Level 3. Suppose the model returns something that fails validation — a missing field, a number out of range. Instead of giving up, the system can hand the error BACK to the model — "that failed validation because the confidence value was above 1; please correct it" — and ask again. The model, seeing its own mistake described, usually fixes it.

This little loop — produce, check, feed the problem back, try again — is a miniature version of a much bigger idea called "reflection," which you will meet properly in Chapter 7. Notice the shape: the model is fallible, so we wrap it in a checking process that catches and corrects errors. That shape — a careful control loop around a fallible generator — is one of the deepest recurring themes in all of agentic engineering.
callout: A careful control loop around a fallible generator — the deepest recurring shape in agentic engineering.

## THEORY
heading: 5.5  Why this is the doorway to tools
body:
Here is the connection that makes this chapter pivotal. When an agent uses a tool (Chapter 6), what actually happens under the hood is that the model produces STRUCTURED OUTPUT describing which function to call and with what arguments — something like: "call the function get_weather, with the argument city set to Tokyo." That is just structured data of a particular shape.

So tool use is not a separate, mysterious capability. It is structured output, formalized and given a dedicated channel by the model's API. Everything you understand about getting reliable, well-shaped data from a model applies directly to getting reliable, well-shaped TOOL REQUESTS from it. Master structured output, and tool calling — the engine of agents — becomes almost obvious.
callout: Tool use IS structured output in disguise, given a dedicated channel.
