## THEORY
heading: 3.0  The conceptual plumbing
body:
You understand what an LLM is (Chapter 1) and how it behaves (Chapter 2). Now: how do programs actually TALK to one? This chapter explains the conceptual plumbing — the shape of a request, the idea of "messages" with "roles," and how the industry settled on one common, interchangeable interface so you can move between providers like Groq and NVIDIA NIM without rewriting anything.

There is nothing to run here; this is the mental model that everything from prompting to tools quietly depends on.
callout: Messages and roles are the single most important structure in all of agentic AI.

## THEORY
heading: 3.1  An LLM is a service you call over the network
body:
When you use a cloud LLM, the model itself lives on the provider's servers. Your program sends a request over the internet — very much like calling a REST API — and receives a response. You are already completely at home with this idea from your REST and REST Assured background: build a request, send it, read the response.

The comparison is almost exact. A REST call: send an HTTP request with a body, get a response body. An LLM call: send a request describing the conversation, get the model's reply.

Two things from earlier chapters shape this call. It is STATELESS (Chapter 2) — the provider remembers nothing between calls; each request must carry everything the model needs to see. And it is billed and limited by TOKENS (Chapter 2), counting both the text you send and the text you receive.

So the central question becomes: what exactly do you put in the request? The answer is a list of MESSAGES.
callout: An LLM call is a stateless, token-metered network request — just like calling a REST endpoint.

## THEORY
heading: 3.2  Messages and roles — the heart of every LLM call
body:
You do not send the model one blob of text. You send an ordered LIST of messages, and each message carries a ROLE that tells the model who is "speaking." This structure is the single most important shape in all of agentic AI, because everything — prompts, memory, tool use — is expressed through it.

The roles you will meet:

SYSTEM — instructions that set up the model: who it is, what it should do, the rules it must follow, and how to format its answer. Think of it as the model's "job description," usually placed first. This is where you shape behavior (all of Chapter 4).

USER — input from the human, or from your program acting on the human's behalf. The actual question or request.

ASSISTANT — the model's own previous replies. You include these when you want the model to be aware of what it already said (i.e., to continue a conversation).

TOOL — results handed back from a tool the model asked to use. This role becomes important in Chapter 6; for now, just know it exists.
snippet:
system:    "You are a helpful, concise tutor."
user:      "What is a token?"
assistant: "A token is a small chunk of text the model reads and writes."
user:      "Give me an example."
snippetExplanation: What this shows: A conversation is simply an ordered list of role-tagged messages. The first sets the model's job. Then the human and the model alternate. To ask a follow-up, you send the WHOLE list again — the earlier turns included — because the model has no memory of its own (Chapter 2). The list IS the conversation; there is no hidden session on the server.
callout: The list of messages IS the conversation. You carry it with you on every call.

## THEORY
heading: 3.3  What comes back — the response
body:
The provider's response contains more than just the answer text. Conceptually, it carries three things.

THE GENERATED TEXT: the assistant's reply — usually the part you want.

A "FINISH REASON": WHY the model stopped. This is genuinely useful to know about. "stop" means it finished naturally (good). "length" means it hit the maximum output length and was CUT OFF (Chapter 2) — your answer is incomplete. "tool_calls" means instead of writing text, the model is asking to use a tool (Chapter 6).

TOKEN USAGE: how many tokens were in the input and the output. This is your running meter for cost and for staying inside limits.

Knowing that "finish reason" exists already makes you a more careful thinker: if an answer looks truncated, an experienced developer immediately suspects it hit the length limit rather than assuming the model "gave up."
callout: If a reply looks cut off, suspect a "length" finish reason — not that the model gave up.

## THEORY
heading: 3.4  Key request settings (conceptual)
body:
Beyond the messages, a request carries a few settings you have essentially already met.

WHICH MODEL to use (Chapter 2's "fit, not size" applies). TEMPERATURE — predictable vs. creative (Chapter 2); low for agents. A MAXIMUM OUTPUT LENGTH — a cap on how many tokens the reply may use, to protect cost and prevent runaway answers; set it too low and you get the "length" cut-off from 3.3. Optionally, STREAMING — receive the reply token by token as it is produced (Chapter 2), for that live "typing" feel.

You do not need to memorize these as settings to configure; understand them as the handful of dials that shape a call. The messages decide WHAT is asked; these dials decide HOW the answer is produced.
callout: Messages decide WHAT is asked; the dials (model, temperature, output length, streaming) decide HOW it is answered.

## THEORY
heading: 3.5  The "OpenAI-compatible" standard — one interface, many providers
body:
Here is a fact that quietly makes your life much easier. Although there are many LLM providers, most of them expose the SAME request-and-response shape — the "messages with roles" format described above. This common shape is widely called the "OpenAI-compatible" format, because it was popularized by OpenAI's chat API and then adopted broadly.

The practical consequence is powerful: learn ONE way of talking to a model, and you can talk to MANY providers, usually by changing nothing more than an address and a key.

This is exactly the "program to an interface, swap the implementation" idea you know from Java and Spring. You code against one interface (the common message format), and you can inject a different provider behind it — Groq today, NVIDIA NIM tomorrow — without changing the logic that uses it. It is dependency injection, applied to language-model providers.

Why this matters for you specifically: it means you are never locked in. If one provider is slow, expensive, deprecated, or down, you switch. This interchangeability is also what makes the free stack viable for learning.
callout: One interface, many providers — dependency injection applied to LLMs. You are never locked in.

## THEORY
heading: 3.6  The free provider stack for learning
body:
You will do your hands-on practice (in LevelShift's build phases) with free cloud providers. Here is the landscape, at the level of understanding — not setup.

GROQ — known for being extremely FAST at producing responses, thanks to specialized hardware. Speed matters a lot for agents, which make many calls in a loop, so Groq is a great primary choice for learning. It offers a free tier, serves strong open models, and speaks the common OpenAI-compatible format.

NVIDIA NIM — NVIDIA's offering (via their developer site) provides free access to many open models and also speaks the OpenAI-compatible format. A good alternate — useful for trying different models.

LOCAL MODELS (e.g., via a tool called Ollama) — you can also run smaller open models directly on your own machine, offline. They too can present the same common interface. Handy when you want zero network dependency, at the cost of speed on ordinary hardware.

Because all of these share the one interface, the concepts in this book apply uniformly. Switching your practice from Groq to NIM will be a trivial change — a direct payoff of the standardization in 3.5.
callout: Groq (fast, primary), NVIDIA NIM (alternate), and local models (offline) — all speak the same interface.

## THEORY
heading: 3.7  Rough edges you should expect (conceptually)
body:
Because an LLM call is a network call to a shared service, the usual realities of calling remote services apply — and you already know these from building resilient systems.

RATE LIMITS: free tiers restrict how many requests or tokens you may use per minute. Exceed them and you are told to slow down (the classic "too many requests" response). Real systems wait and retry politely.

FAILURES AND TIMEOUTS: the network or the service can hiccup. Robust code retries transient failures and sets timeouts so nothing hangs forever.

CHANGING MODELS: model names get retired and replaced over time. Code that hard-codes a specific model may need updating later.

None of this is unique to AI — it is ordinary remote-service discipline (the same instincts behind retries, timeouts, and circuit breakers in your Spring services). We revisit it properly under reliability in Chapter 17.
callout: Talking to an LLM inherits every normal concern of talking to a remote API — rate limits, timeouts, retries.
