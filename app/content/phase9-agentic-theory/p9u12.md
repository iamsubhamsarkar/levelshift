## THEORY
heading: 12.0  Convenience over the same primitives
body:
Up to now, this book has built every idea from first principles: messages, prompting, structured output, tools, the loop, memory, retrieval. That was deliberate. Because you now understand the primitives, the many "agent frameworks" you will hear about lose their mystery — each one is just a convenient package around the SAME primitives.

This chapter surveys the 2026 framework landscape, explains how to think about choosing one, and shows that no framework can do anything the primitives cannot; it merely does it with less plumbing.
callout: Frameworks are convenience over the same primitives. None can do anything the primitives cannot.

## THEORY
heading: 12.1  Do you even need a framework?
body:
The honest answer, especially at first, is often NO. A single agent loop with a few tools can be written directly and understood completely. Frameworks start to earn their place when you need things that are tedious to build by hand: ready-made plumbing (retries, streaming, tool wiring, memory handling); complex control flow (branching, looping, pausing for human approval, saving and resuming progress); coordinating multiple agents with less boilerplate (Chapter 14); built-in connections to evaluation and observability tools (Chapters 15-16); and a shared vocabulary and structure so a team builds consistently.

Frameworks also have costs: a learning curve, extra layers to debug through when things break, rapid version churn, and sometimes hidden prompts they inject that you did not write. The mature approach — and the reason this book taught primitives first — is to understand what is happening underneath, adopt a framework when it clearly saves more than it costs, and keep the ability to drop down to direct calls when needed.

The guiding principle: frameworks are CONVENIENCE over the same primitives. Choose based on fit, not on hype.
callout: Choose a framework based on fit, not hype — and only when it clearly saves more than it costs.

## THEORY
heading: 12.3  The major Python frameworks in 2026
body:
You do not need to master these; you need to recognize what each is FOR. (Names and details shift over time; the roles are what endure.)

LANGCHAIN and LANGGRAPH. LangChain is the largest ecosystem — connectors for nearly every model, vector store, and data source. LangGraph is its modern core for building agents as a GRAPH: you model the agent as a set of steps (nodes) with defined transitions (edges), including loops and explicit shared state. It excels at complex, controllable flows and things like pausing for human approval and resuming. Its cost is a steeper learning curve. (For a Java developer: the graph-of-steps-with-state idea is much like modeling a process as an explicit state machine or workflow engine.)

CREWAI. An opinionated framework for MULTI-AGENT teams: you define "agents" with roles, "tasks" for them, and a "crew" that coordinates them. Quick for standing up a team of role-playing specialists, at the cost of less low-level control.

STRANDS AGENTS. A lightweight agent toolkit, open-sourced by AWS. Its philosophy is close to this book's: an agent is a model plus tools plus a prompt in a loop. Model-agnostic, works well with AWS services, and supports the tool-sharing standard you will meet next chapter (MCP). A good choice when you want something minimal and close to the primitives.

THE OPENAI AGENTS TOOLKIT. A small, official set of building blocks — agents, tools, "handoffs" (one agent delegating to another), guardrails, and sessions. Clean and modern, with built-in tracing.

OTHERS WORTH KNOWING. LlamaIndex specializes in retrieval and document-heavy applications. There are also type-first toolkits built around the data-validation ideas from Chapter 5, and offerings from major cloud vendors. The space moves quickly; the PRIMITIVES do not.
callout: LangGraph (controllable flows), CrewAI (multi-agent teams), Strands (minimal, AWS), OpenAI toolkit (clean handoffs), LlamaIndex (retrieval).

## THEORY
heading: 12.4  For the Java developer — Spring AI
body:
Since you know Spring, this matters to you specifically. SPRING AI brings agentic building blocks into the Spring ecosystem, in idiomatic Java: a fluent client for talking to chat models (the same message-based idea from Chapter 3, provider-agnostic); tool/function calling via annotated Java methods, so the model can call your Spring beans (Chapter 6, in Java); structured output mapped onto Java objects (Chapter 5, in Java); retrieval support with vector-store abstractions (Chapters 10-11); and integration with everything you already use — dependency injection, configuration, the Spring runtime.

Why this is significant for your journey: you can learn and prototype agents in Python (which the ecosystem centers on), and then build PRODUCTION agents in Java/Spring if that is your stack. The concepts transfer one-to-one — messages, tools, structured output, retrieval — only the syntax changes. In 2026 many teams do exactly this: prototype fast in Python, ship on the JVM with Spring AI.
callout: Prototype in Python, ship on the JVM with Spring AI. The concepts transfer one-to-one; only the syntax changes.

heading: 12.5  Raw versus framework, side by side
body:
To make the "same primitives" point concrete, picture the same weather agent two ways. Written from scratch (the loop you understood in Chapter 7), it is a modest amount of code you fully control. Written with a framework, it might look like this word-picture.
snippet:
define a tool: get_weather(city) -> returns the forecast
create an agent with:
    - instructions: "use tools; don't guess facts you can look up"
    - the get_weather tool
ask the agent: "Weather in Tokyo? Umbrella?"
snippetExplanation: What this shows: The framework version is shorter and hands you retries, tracing, and memory "for free." But look closely — it is doing EXACTLY what your hand-built loop did. Declaring a tool is the tool description from Chapter 6. "Instructions" is the system prompt from Chapter 4. "Ask the agent" is the loop from Chapter 7. Nothing is conceptually new; the framework just wrote the plumbing for you.

## THEORY
heading: 12.6  How to choose
body:
A rough guide, tying back to needs you now recognize. Learning / full transparency: build it raw (as in this book). Single agent, want free plumbing: a lightweight toolkit (Strands, OpenAI Agents toolkit, a type-first option). Complex, controllable flows with loops: LangGraph. Role-based multi-agent, quick to build: CrewAI. Document/retrieval-heavy application: LlamaIndex (or LangChain). Deploying on AWS: Strands (with AWS services). A Java / Spring production stack: Spring AI.

The meta-advice: prototype the simplest version first to validate the idea; adopt a framework when a specific need justifies it; prefer lighter frameworks unless you truly need heavy machinery; keep provider-agnosticism (Chapter 3) — most frameworks let you swap models; and do not marry a framework — wrap framework-specific code behind your own interfaces so you can change later.
callout: Prototype simplest first. Adopt a framework when a specific need justifies it. Don't marry a framework.

## THEORY
heading: 12.7  Pitfalls when adopting a framework
body:
HIDDEN PROMPTS. Many frameworks inject their own system prompts. Turn on their tracing and READ what is actually sent to the model — surprises live here. Your from-scratch understanding is what lets you spot them. LEAKY ABSTRACTIONS. When something breaks, you debug through the framework's layers; knowing what SHOULD be happening is what saves you. VERSION CHURN. These libraries change fast — pin versions and read migration notes. OVER-ABSTRACTION. Do not reach for a graph or a crew when a single function call would do. LOCK-IN. Isolate framework code behind interfaces you own. LOSING PROVIDER FLEXIBILITY. Confirm the framework supports the free providers (Groq, NVIDIA NIM) you want.
callout: Hidden prompts, leaky abstractions, version churn, lock-in — your from-scratch knowledge is your best defense.
