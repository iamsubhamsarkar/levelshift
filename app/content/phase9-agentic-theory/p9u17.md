## THEORY
heading: 17.0  Shipping it
body:
Your agent is understood (Chapters 1-14), measurable (Chapter 15), and safe and observable (Chapter 16). This chapter is about SHIPPING it — turning an idea that works on someone's screen into a real service that many people can rely on.

Your background in building and deploying REST services means most of this will feel familiar; the new parts are the concerns specific to LLMs — cost, latency, and the peculiar reliability challenges of depending on a slow, pay-per-call, non-deterministic model.
callout: Shipping an agent is the production discipline you know — with a slow, metered, non-deterministic model at the center.

## THEORY
heading: 17.1  What "production" adds
body:
A demo runs once, on one machine, for one friendly user. Production means: it is a SERVICE that others call, many at once, reliably; it handles FAILURE gracefully (the provider is down, you hit a rate limit, a call times out); it controls COST and LATENCY at real volume; it is OBSERVABLE and SAFE (Chapter 16) under real and sometimes hostile traffic; and it can be DEPLOYED and UPDATED — versioned, rolled out carefully, rolled back quickly.

This is the same production discipline you already apply to a service — with the twist that the "business logic" at the center is a non-deterministic, latency-heavy, metered model.
callout: Production adds: many concurrent callers, graceful failure, cost and latency control, safety, and careful rollout.

## THEORY
heading: 17.2  Packaging an agent as a service
body:
The usual way to make an agent available is to wrap it behind an interface others can call — most commonly a web API, exactly as you would expose a service with REST. A request comes in with the user's goal; the service runs the agent; the answer comes back. You would naturally place your input and output guardrails (Chapter 16) right at this boundary.
snippet:
a request arrives with the user's goal
    -> check the input (guardrails)
    -> run the agent loop
    -> clean/check the output (guardrails)
    -> return the answer
snippetExplanation: What this shows: The agent sits inside an ordinary service, with safety checks guarding the entrance and the exit — structurally identical to a web controller that validates a request, does its work, and validates the response before returning it. A few service concerns deserve special attention because agents stress them: KEEP THE SERVICE STATELESS, STORE STATE OUTSIDE (conversation history and memory live in an external store, keyed by a session identifier, so you can run many copies); EXPECT SLOW, CONCURRENT REQUESTS (model calls take seconds, and an agent makes several per task); STREAM FOR LONG RESPONSES so the user sees progress; and USE A JOB QUEUE FOR VERY LONG TASKS (accept the task, hand back a ticket, let the caller check back).
callout: An agent is an ordinary service with guardrails at the boundary. Keep it stateless; store state outside; expect slow, concurrent requests.

## THEORY
heading: 17.3  Managing cost
body:
Because agents multiply model calls — a loop is many calls; a team of agents is many more — cost becomes a first-class design concern at scale. The main levers:

RIGHT-SIZE THE MODEL FOR EACH STEP. Use the smallest model that passes your evaluations (Chapter 15) for routine decisions, and reserve a large, expensive model only for the genuinely hard step. This is often the single biggest saving. (It is why Chapter 2 told you to retire "biggest is best.")

CACHE REPEATED WORK. If the same question comes in again, return the stored answer instead of calling the model again. A gentler version reuses the answer for questions very SIMILAR in meaning (using embeddings from Chapter 10, carefully). Many providers can also reuse the processing of a long, unchanging prompt prefix, so structuring your prompt with the stable part first saves both cost and time.

TRIM WHAT YOU SEND. System prompts are re-sent on every step of a loop; keep them tight. Summarize long histories (Chapter 9). Return concise tool results (Chapter 6). Every trimmed token is saved on every step.

CAP THINGS. Limit the output length and the number of steps per task, so a single request cannot run away with your budget.

WATCH AND ALERT. Track cost per request in your traces (Chapter 16) and alert on spikes — a looping or abused agent can quietly run up a large bill.
callout: Right-size the model per step (the biggest saving), cache, trim, cap, and alert. These habits also keep you inside free-tier limits.

## THEORY
heading: 17.4  Managing latency
body:
Agents can feel slow because every step is a network round-trip to a model. Ways to reduce the wait, real and perceived:

FEWER STEPS: a simpler architecture (Chapter 8), good prompts, and planning that prevents wandering all cut the number of round-trips. FASTER MODELS: this is where a provider like Groq, known for speed, genuinely helps. DO INDEPENDENT WORK IN PARALLEL (Chapter 8). STREAM the answer so the user perceives progress even when the total time is unchanged. ROUTE BY DIFFICULTY: send easy requests to a small, fast model and escalate only the hard ones to a big model — Chapter 8's routing pattern applied to model choice, a core 2026 technique.

As with a REST service, it helps to set explicit latency targets and design toward them, rather than hoping for the best.
callout: Fewer steps, faster models, parallelism, streaming, routing by difficulty — the levers for latency.

## THEORY
heading: 17.5  Reliability
body:
External model providers fail, throttle, and change. You engineer around this — and most of it is the resilient-service playbook you already know.

RETRY TRANSIENT FAILURES with a growing wait between attempts (so you don't hammer a struggling service). SET TIMEOUTS on every model and tool call, so nothing hangs forever. HAVE A FALLBACK. If the primary provider or model fails, switch to a backup. This is where the provider-agnostic thinking from Chapter 3 pays off richly: because you were never locked to one provider, failing over from Groq to NVIDIA NIM (or to a smaller model, a cached answer, or a safe canned reply) is straightforward. USE A CIRCUIT BREAKER: stop calling a dependency that is clearly failing. MAKE ACTIONS SAFE TO RETRY (idempotent): since an agent may retry a tool, a retried "send payment" must not charge twice — use the same idempotency-key idea you would in any careful integration. DEGRADE GRACEFULLY: a partial answer with "I couldn't complete this part" beats an error page.

The parallel is exact: this is the retry, timeout, fallback, and circuit-breaker discipline of resilient microservices — the "remote dependency" just happens to be a language-model provider now.
callout: Retry with backoff, timeouts, fallback (Groq to NIM), circuit breaker, idempotency, graceful degradation — the resilient-service playbook.

## THEORY
heading: 17.6  Secrets, configuration, and rolling out changes
body:
SECRETS. Never put API keys in code. Keep them in a secret manager or injected configuration, and rotate them if they leak — the same rule you apply to any production credential.

CONFIGURATION PER ENVIRONMENT. Development, staging, and production may use different models, limits, and providers. And, from Chapters 4 and 15, keep prompts and model choices VERSIONED so you can attribute a behavior change to a specific change and roll it back.

ROLL OUT CAREFULLY. Release a new prompt, model, or agent gradually (to a small slice of traffic first), compare its quality against the old version using your evaluations (Chapters 15-16), and roll back quickly if quality drops. This is the same canary-release caution you would use for any risky change.
callout: Secrets in a manager (never in code), config per environment, versioned prompts, gradual rollout with fast rollback.

## THEORY
heading: 17.7  Where agents run (deployment options)
body:
You do not need deep operational detail here — just awareness of the choices.

A CONTAINERIZED SERVICE. Package the agent service and run it on standard infrastructure, scaling out by running more copies (kept possible by the stateless design of 17.2). The familiar, portable baseline.

SERVERLESS FUNCTIONS. Good for spiky or low-volume workloads, but beware: cold starts and strict time limits clash with long agent runs. Use for short tasks, or trigger a background job for long ones.

MANAGED AGENT PLATFORMS. In 2026, cloud providers offer services that handle much of the undifferentiated plumbing — managed access to many models, managed agent orchestration, managed retrieval, and managed safety guardrails. On AWS, for example, there is a managed model-and-agent service plus a lightweight open agent toolkit (Strands) with strong cloud and MCP integration.

THE JVM / SPRING PATH. If your organization runs on Java, you can deploy agents as ordinary Spring services using Spring AI (Chapter 12) — the same REST, dependency-injection, observability, and deployment pipeline you already operate, with the agentic pieces layered in.

A recurring payoff: because you coded against the common, interchangeable model interface (Chapter 3), moving between providers — or from a free learning stack to an enterprise platform — is largely a configuration change, not a rewrite.
callout: Containers (portable baseline), serverless (short tasks), managed platforms, or the Spring/JVM path — the interchangeable interface makes moving a config change, not a rewrite.

## THEORY
heading: 17.8  A production readiness mindset (checklist)
body:
Before calling an agent "ready," you should be able to say yes to these — a distillation of the last several chapters.

RELIABILITY: retries with backoff; timeouts everywhere; a provider or model fallback; caps on steps and cost; retry-safe actions. COST AND LATENCY: right-sized models per step; caching where sensible; trimmed prompts and concise tool results; cost and latency tracked with alerts. SAFETY AND OBSERVABILITY (Chapter 16): input, output, and action guardrails at the boundary; injection defenses and least privilege; human approval on high-stakes actions; tracing on every request; no secrets or personal data in logs. QUALITY AND OPERATIONS (Chapter 15): an evaluation suite gating changes; versioned prompts and models; careful rollout with fast rollback; secrets in a manager; health checks and the ability to scale out.
callout: Reliability, cost/latency, safety/observability, quality/operations — say yes to all four before calling an agent "ready."
