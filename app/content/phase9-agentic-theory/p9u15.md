## THEORY
heading: 15.0  Home turf, with one hard twist
body:
This is home turf for you — you come from QA and REST Assured — but with one hard twist: agents are NON-DETERMINISTIC. The same input can produce different outputs, both perfectly valid. The exact-match assertions you rely on in ordinary testing break here.

This chapter explains how to evaluate and test agentic systems properly: what to measure, how to grade output that varies, how to test the PROCESS and not just the answer, and how to build a safety net so you can change prompts and models without fear. Evaluation is not optional; it is the discipline that separates engineering from wishful thinking.
callout: Agents are non-deterministic. Evaluation is the discipline that separates engineering from wishful thinking.

## THEORY
heading: 15.1  Why you can't test agents like ordinary code
body:
In your REST Assured tests, you assert exact results: call this endpoint, expect exactly this response. With an LLM, ask it to "summarize this" twice and you get two different summaries — both correct. An exact-match assertion would fail on perfectly good output.

So the mindset shifts. Ordinary testing: assert that the output EQUALS the expected value. Agent evaluation: assert that the output SATISFIES criteria — often with a SCORE and a THRESHOLD — measured across MANY cases, and tolerating variation.

You move from a single pass/fail on one run to MEASURING QUALITY over a set of cases — closer to performance testing (where you check that most requests come in under a latency target) than to a strict unit test. Your instincts for building test suites, fixtures, and continuous-integration gates all carry over; only the style of the assertion changes.
callout: From "output EQUALS expected" to "output SATISFIES criteria, measured across many cases, tolerating variation."

## THEORY
heading: 15.2  The evaluation mindset — cases, scorers, thresholds
body:
Evaluation rests on a few building blocks that map neatly onto testing concepts you already use.

A DATASET OF CASES. A collection of test inputs, optionally paired with expected outputs or reference answers. These are your fixtures. Start small — ten to fifty hand-picked cases — and grow over time. Crucially, every time you find a real failure, ADD it as a new case, so it can never quietly return (regression testing).

A SCORER. A way to grade an output — as pass/fail or on a scale — against your criteria or a reference answer. This is your "assertion," but graded rather than binary.

A THRESHOLD. The bar the overall score must clear — "at least 90% correct on the classification cases," or "average quality of at least four out of five." This is your continuous-integration gate.

The golden rule: DEFINE SUCCESS BEFORE YOU BUILD. If you cannot articulate what "good" means for your agent, you cannot build it or improve it responsibly.
callout: Cases (fixtures), a scorer (graded assertion), a threshold (CI gate). Define success BEFORE you build.

## THEORY
heading: 15.3  Levels of evaluation — unit, integration, end-to-end
body:
Agentic systems, like ordinary software, deserve evaluation at multiple levels. The parallel to unit / integration / end-to-end testing is exact.

COMPONENT LEVEL (like unit tests). Does one prompt produce the right structured output? Does each tool work correctly in isolation? (Tools are ordinary code — you can unit-test them exactly as you always have.) For retrieval systems: did we fetch the RIGHT chunks?

TRAJECTORY LEVEL (like integration tests) — UNIQUE TO AGENTS. Did the agent take GOOD STEPS? Not just "was the final answer right," but "was the PROCESS sensible": did it call the right tools, in a reasonable order, with valid arguments? Did it avoid looping? Did it stop at the right time?

END-TO-END LEVEL (like system tests). Given the goal, is the FINAL result correct, useful, and safe? This is what the user ultimately cares about.

Why both process AND outcome? Because an agent can reach the right answer by luck through a terrible, expensive path — or take a sensible path that produces a wrong answer because a tool was down. Measuring only the final answer hides both problems.
callout: Component, trajectory, end-to-end. Measure both the PROCESS and the OUTCOME — each hides bugs the other misses.

## THEORY
heading: 15.4  How to grade output that varies
body:
There are several ways to score non-deterministic output. Prefer the cheap, reliable ones whenever the task allows.

RULE-BASED SCORING (best when the output is constrained). When the output is a fixed choice or a structured value, you CAN assert precisely. Did the classifier output exactly "BLOCKER"? Does it parse as valid JSON of the right shape (Chapter 5)? For code tasks, the strongest scorer of all: RUN the code, or run the tests, and use pass/fail. If you designed for structured output (Chapter 5), much of your evaluation becomes plain assertions.

SIMILARITY SCORING (for free text with a reference answer). Use the embeddings idea from Chapter 10: measure how CLOSE in meaning the output is to a reference answer. A high closeness means "semantically right," tolerating differences in wording.

LLM-AS-A-JUDGE (the 2026 workhorse for subjective quality). Use one LLM to GRADE another LLM's output against a rubric. This handles qualities no simple rule can capture — helpfulness, tone, faithfulness. It is powerful but has known biases you must manage: give it a CLEAR rubric; prefer simple judgments (a 1-to-5 score, or "which of these two is better?"); use a strong model as the judge at low temperature; and CALIBRATE it against human judgments on a sample before trusting it.

HUMAN EVALUATION (the gold standard, but expensive). People review a sample of outputs. Slow and costly, so use it to CALIBRATE the automated scorers and to spot-check — not for every run.
callout: Rule-based (best when constrained), similarity (free text), LLM-as-judge (subjective), human (gold standard). Prefer the cheap, reliable ones.

## THEORY
heading: 15.5  Trajectory evaluation — testing the process
body:
This is the evaluation skill unique to agents. Recall that an agent's run produces a TRAJECTORY — the ordered sequence of thoughts, tool calls, arguments, and observations, ending in the final answer (Chapter 7). You can evaluate that trajectory, not just the answer.

What to check on a trajectory: TOOL SELECTION (did it call the appropriate tools?); ARGUMENTS (were they valid and sensible?); ORDER (was the sequence reasonable — it didn't check the weather before knowing the city?); EFFICIENCY (did it finish in a reasonable number of steps, without looping?); NO FORBIDDEN ACTIONS (did it avoid any tool it should not have used?); STOPPING (did it stop at the right time?).

There are two broad ways to judge a trajectory: compare it against an "ideal" sequence you defined, or use an LLM-as-judge to assess whether the process was reasonable when there is no single correct path. Importantly, capturing trajectories is also the foundation of OBSERVABILITY (Chapter 16) — the same recorded run you evaluate offline is what you monitor in production.
callout: Evaluate the trajectory: tool selection, arguments, order, efficiency, forbidden actions, stopping. It is also the foundation of observability.

## THEORY
heading: 15.6  Handling non-determinism — measure a pass rate
body:
Here is the key adaptation that makes testing agents work: because the same input can yield different outputs, you run each case SEVERAL times and measure a PASS RATE rather than a single true-or-false.

A case that passes five times out of five is robust. A case that passes three times out of five is FLAKY — it needs attention: a tighter prompt, a lower temperature, more constraints, a better tool description. This is exactly how you would think about a flaky integration test — except here the flakiness is inherent to the technology, so you QUANTIFY it and drive it down deliberately.

"It worked once" proves nothing about a non-deterministic system. Only a pass rate across repeated runs, over a representative set of cases, tells you whether the agent is actually reliable.
callout: Run each case several times; measure a pass rate. "Three out of five" means flaky — tighten it.

## THEORY
heading: 15.7  What to measure beyond correctness
body:
A trustworthy evaluation tracks more than "is the answer right." Watch, per run (and later in production, Chapter 16): QUALITY (task success rate, judge scores, exact matches where they apply); COST (tokens and money per task — multi-step agents add up quickly); LATENCY (how long it takes end to end; how many steps and model calls); RELIABILITY (the pass rate across repeated runs); TOOL BEHAVIOR (how often tools error or the wrong tool is chosen); SAFETY (how often it violates a policy or takes an unsafe action — Chapter 16); and FOR RETRIEVAL SYSTEMS (did retrieval fetch the right material, and did the answer stay faithful to it?).

A "better" agent almost always trades among these — more quality for more cost, or less latency for a bit less quality. Making these trade-offs VISIBLE is what turns a decision from a guess into an evidence-based choice.
callout: Measure quality, cost, latency, reliability, tool behavior, and safety — not just correctness. Trade-offs must be visible.

## THEORY
heading: 15.8  The payoff — a regression safety net
body:
The reward for building an evaluation dataset is the ability to change things WITHOUT fear.

Run the evaluation suite on every meaningful change — a prompt edit, a model swap, a tool change, a framework upgrade — exactly like running your test suite in continuous integration. GATE on the thresholds: block a change if quality drops below the bar. GROW THE DATASET FROM REAL FAILURES: every genuine failure becomes a new case, so it can never silently return. Over time this flywheel compounds your agent's quality.

Because models get retired and providers change (Chapter 3), this suite is also what lets you migrate from one model or provider to another — say, from Groq to NVIDIA NIM — with evidence that quality held, rather than crossed fingers.
callout: An evaluation suite lets you change prompts, swap models, and migrate providers with EVIDENCE that quality held.

## THEORY
heading: 15.9  Pitfalls
body:
"IT WORKED ONCE." One good run proves nothing — measure over a dataset, with repeated runs. NO BASELINE. Always compare a new, fancier approach against the simplest one (Chapter 8) and against the previous version — complexity must earn its keep. OVER-TRUSTING THE JUDGE. Calibrate the LLM-judge against humans; combine it with rule-based scorers. GRADING ONLY THE FINAL ANSWER. Evaluate the trajectory too. A TINY OR STALE DATASET. Grow it from real failures and keep it representative. IGNORING COST AND LATENCY. A "smarter" agent that costs ten times as much may be worse overall.
callout: "It worked once" is not evidence. Keep a baseline, evaluate trajectories, watch cost and latency.
