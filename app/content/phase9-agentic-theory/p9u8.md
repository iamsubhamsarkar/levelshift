## THEORY
heading: 8.0  The design-thinking layer
body:
You now understand a working agent (Chapter 7). This chapter steps back to ask: how do you STRUCTURE agentic systems as reusable designs? Just as you reach for known patterns in Java — Strategy, Chain of Responsibility, Pipeline — instead of improvising, an agent developer chooses from a catalog of proven architectures.

Knowing this catalog lets you pick the RIGHT shape for a problem — almost always the simplest one that works — rather than defaulting to complexity.
callout: Choosing an architecture is mostly the discipline of NOT over-engineering.

## THEORY
heading: 8.1  The governing principle, restated
body:
"Use the least agentic thing that works" (Chapter 1) is, above all, a rule about ARCHITECTURE. Choosing a design is mostly the discipline of NOT over-engineering. A hard lesson the field learned by 2026: elaborate multi-agent contraptions often perform WORSE than a single well-designed agent — more cost, more latency, more unpredictability, less reliability.

A practical order to consider, stopping at the first that works: (1) A single model call with structured output? (Chapters 3-5). (2) A single model call that uses one tool? (Chapter 6). (3) A single agent loop? (Chapter 7). (4) A fixed workflow of steps (some by the model, some by plain code)? (5) A router that sends work to specialists? (6) A full multi-agent system? (Chapter 14).

Higher numbers mean more power AND more ways to fail. Every step up the list should be justified by a real need, not by ambition.
callout: Climb the complexity ladder one rung at a time — and only when a real need justifies it.

## THEORY
heading: 8.2  Workflows vs agents — a distinction worth internalizing
body:
A key modern framing separates two ways to use LLMs.

A WORKFLOW is when the model's calls are arranged along PREDEFINED paths that YOU designed. You decide the sequence of steps; the model supplies the intelligence at each step. Predictable, testable, cheaper.

An AGENT is when the model itself DECIDES the steps and which tools to use, at runtime. More flexible and able to handle open-ended tasks, but less predictable.

An important truth: most real-world "AI features" are actually WORKFLOWS, not fully autonomous agents — and that is a good thing. Reserve genuine (dynamic) agents for problems where you truly cannot lay out the steps in advance.

The Java parallel: a WORKFLOW is like a service method you wrote that calls a fixed sequence of steps in order — you control the flow. An AGENT is like handing control to something that decides its own execution path at runtime. You would only do the latter when the path genuinely cannot be known beforehand.
callout: Most real "AI features" are — and should be — workflows, not fully autonomous agents.

## THEORY
heading: 8.3  Workflow pattern — prompt chaining (a pipeline)
body:
Break a task into a fixed SEQUENCE of model steps, each feeding the next — like a pipeline, or a Unix command piping into the next. For example, to write an article: first produce an outline, then expand the outline into prose, then polish the prose. Each step focuses on one thing and does it well.

WHEN TO USE IT: when a task naturally splits into ordered subtasks, each simpler than the whole. Splitting improves quality because each call has one clear job.

A useful refinement is to add a CHECK between steps — a gate that verifies the output so far and stops or retries if something is off (for instance, "is this outline actually about the requested topic?").

TRADE-OFF: more steps mean more total time and cost, but each step is simpler and more reliable, and you can examine each independently.
callout: Prompt chaining: ordered subtasks, each simpler than the whole — optionally with a check between steps.

## THEORY
heading: 8.4  Workflow pattern — routing (a dispatcher)
body:
First classify the input, then send it to the specialized handler best suited for it. This is the Strategy pattern, or a switch on intent: a customer message might be routed to a billing handler, a technical handler, or a sales handler, each with its own tailored prompt and its own tools.

WHEN TO USE IT: when distinct kinds of input deserve distinct handling, and cramming them all into one giant prompt would hurt quality. Routing lets each handler be focused and simple. It is extremely common in customer support and any multi-topic assistant.

TRADE-OFF: one extra classification step, and the risk of misrouting (softened by clear categories and a sensible "everything else" fallback).
callout: Routing = classify first, then dispatch to the right specialist handler.

## THEORY
heading: 8.5  Workflow pattern — parallelization (fan-out, fan-in)
body:
Run several model calls at the SAME TIME, then combine their results. Two common flavors.

SECTIONING: split a task into independent parts, handle them in parallel, and merge — for example, summarize ten documents simultaneously, then synthesize one overall summary.

VOTING: run the SAME task several times (or with slightly different prompts) and aggregate — take the majority answer, or the best of several. This raises confidence on tricky judgments ("is this content safe?" — ask three times, take the majority).

WHEN TO USE IT: when subtasks are independent (sectioning) or when you need higher confidence (voting). Parallelization can cut waiting time and improve accuracy.

TRADE-OFF: several times the cost, the added complexity of doing things concurrently, and the need to merge results sensibly.
callout: Parallelization: sectioning (independent parts) or voting (same task several times for confidence).

## THEORY
heading: 8.6  Evaluator-optimizer, and orchestrator-workers
body:
EVALUATOR-OPTIMIZER (a generate-and-critique loop). One model call generates a result; another (or the same one wearing a "critic" hat) evaluates it and gives feedback; this repeats until the evaluator is satisfied or a limit is reached. This is reflection (Chapter 7) promoted to an architecture with two explicit roles. It shines when quality is critical AND you have clear criteria — especially when the evaluator can lean on something objective, like running a test or checking a result.

ORCHESTRATOR-WORKERS. A central "orchestrator" model call looks at the task, dynamically breaks it into subtasks, hands each to a "worker" call, and then combines the results. The distinctive feature is that the subtasks are NOT fixed in advance — the orchestrator decides them based on the specific input. For example, "make this change across an unknown set of files" — the orchestrator first discovers which files are involved, then dispatches a worker for each. This one straddles the line between workflow and agent: the orchestrator behaves agentically (it plans dynamically), while the workers are constrained. It is the conceptual bridge to true multi-agent systems (Chapter 14).

TRADE-OFFS: evaluator-optimizer costs extra rounds and needs a meaningful critic. Orchestrator-workers is the most complex workflow pattern, with real coordination overhead — justify it before reaching for it.
callout: Orchestrator-workers is the bridge to multi-agent systems: dynamic planning up top, constrained workers below.

## THEORY
heading: 8.7  Agent pattern — the single autonomous agent
body:
This is the Chapter 7 agent: one model in a loop with tools, deciding its own steps until done. It is the DEFAULT agent pattern and the right choice for MOST agentic tasks.

WHEN TO USE IT: open-ended tasks where the number and order of steps cannot be fixed in advance, but a single capable agent with the right tools can handle it — a coding assistant, a research assistant, a data question-answering agent.

ITS STRENGTHS: simple to reason about; a single context; one place for the logic; no inter-agent coordination bugs. Its LIMITS: too many tools confuse it; very long tasks strain its context; it cannot truly parallelize itself. When you hit those limits, consider routing or multi-agent — but only then.
callout: The single autonomous agent is the DEFAULT and right for most agentic tasks. Reach past it only when it hits real limits.

## THEORY
heading: 8.8  Agent patterns — plan-and-execute, and reflection
body:
These two were introduced in Chapter 7; as architectures, their roles are as follows.

PLAN-AND-EXECUTE. The agent produces an explicit plan, then works through it. Its architectural value is ANCHORING a long task against drift and making the intended steps visible — useful when you want a human to approve the plan before execution.

REFLECTION / SELF-CORRECTION. The agent critiques and improves its own work in a loop. As an architecture, pair it with an OBJECTIVE evaluator wherever possible (run a test, validate against a schema, check a calculation) — objective feedback beats the model grading itself.

Both are used when quality or reliability on complex tasks justifies the extra model calls.
callout: Plan-and-execute anchors long tasks; reflection improves quality — best paired with an objective evaluator.

## THEORY
heading: 8.9  A cross-cutting dimension — human-in-the-loop
body:
This is not a standalone pattern but a design choice you can overlay on ANY of the above: insert human checkpoints where autonomy would be risky.

APPROVAL GATES before irreversible or expensive actions — sending money, deleting data, emailing customers, deploying. The agent PROPOSES; a human APPROVES. CLARIFICATION: the agent asks the user when genuinely uncertain, rather than guessing. REVIEW: a human inspects the plan or the final output before it ships.

In 2026, thoughtful human-in-the-loop design is a hallmark of responsible agents. The craft is placing gates at the FEW high-stakes points without burying the user in constant prompts. We return to this in Chapter 16.
callout: Human-in-the-loop overlays on any pattern. The craft is WHERE to place the few high-stakes gates.

## THEORY
heading: 8.10  Where state and context live
body:
Every architecture must answer: where does information live, and how does it flow between steps or agents?

Within a single agent run: in the messages list (Chapter 7). Between steps of a workflow: passed explicitly as one step's output feeding the next — clean and testable. Between agents: you must define a CONTRACT for what is shared; loose, undefined sharing breeds chaos. Across runs, or long-term: persistent memory and retrieval (Chapters 9-11).

A durable design rule, and the same one that keeps large Java systems sane: minimize shared mutable state. Prefer passing explicit, well-shaped data between components (like immutable data objects) over one big shared mutable blob that everything reaches into.
callout: Minimize shared mutable state. Pass explicit, well-shaped data between components.

## THEORY
heading: 8.11  A decision cheat-sheet
body:
If you internalize just this table, you can turn most requirements into a sensible architecture — and reach for complexity only when it earns its place.

## THEORY
heading: 8.12  Anti-patterns
body:
MULTI-AGENT BY DEFAULT: spinning up "a team of agents" for something one agent handles. Adds coordination bugs, cost, and latency. THE GOD AGENT: one agent with forty tools and a three-page prompt. Split it via routing or specialization. HIDDEN SHARED STATE between agents: untraceable bugs — use explicit contracts. NO LIMITS: any loop without a cap is a runaway (Chapter 7). NO EVALUATION: choosing an architecture without measuring whether it beats a simpler baseline (Chapter 15). PREMATURE FRAMEWORK LOCK-IN: adopting a heavy framework before you understand the pattern you need — understand the pattern first, then pick a framework (Chapter 12) if it earns its weight.
callout: The god agent, multi-agent-by-default, hidden shared state, no limits, no evaluation — the classic architecture traps.
