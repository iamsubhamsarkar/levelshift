## THEORY
heading: 13.0  USB-C for AI tools
body:
In Chapter 6 you learned that tools let an agent act, and that each tool is wired into the agent directly. MCP — the Model Context Protocol — solves a bigger problem: how to expose tools, data, and prompts in a STANDARD way, so that ANY MCP-aware agent can use them, across different programs, languages, and vendors.

By 2026 it is the dominant standard for connecting agents to capabilities. This chapter explains what MCP is and why it matters. It is conceptual throughout.
callout: MCP standardizes how agents connect to tools, data, and prompts — across programs and vendors.

## THEORY
heading: 13.1  The problem MCP solves
body:
Before a standard existed, connecting tools to agents was an "everyone builds everything" mess. If you had many applications and many tools or data sources, each application needed custom code to connect to each tool. Your weather tool, written for your agent, could not be reused by a colleague's assistant or a different framework without rewriting the glue.

Without a standard: (number of apps) times (number of tools) custom integrations — it multiplies painfully. With a standard: each app and each tool speaks ONE common protocol, so the connections ADD UP instead of MULTIPLYING.

MCP is an OPEN PROTOCOL that standardizes how applications provide tools and context to LLMs. The analogy that stuck, and that you will hear everywhere: MCP is "USB-C for AI." Just as USB-C is one connector that works across countless devices, MCP is one interface between AI agents and the things that give them capabilities. Build a tool once as an MCP "server," and every MCP-compatible agent can use it — no bespoke glue.
callout: Without a standard, integrations multiply. With MCP, they add up. Build a tool once; every MCP agent can use it.

## THEORY
heading: 13.2  The architecture — hosts, clients, and servers
body:
MCP follows a client-server design with three roles. The names are worth learning because they come up constantly.

HOST: the AI application the person actually uses — a coding assistant, a chat app, or your own agent program. The host contains one or more clients.

CLIENT: lives inside the host and maintains a connection to one server, speaking MCP on the host's behalf.

SERVER: a separate program that EXPOSES capabilities — tools, data, prompts — over MCP. It wraps some functionality: a database, an external API, the file system, or your own custom logic.
snippet:
+--------------------------------+
|  HOST (your agent application) |
|    contains clients  ----------|----> SERVER: weather
|                      ----------|----> SERVER: company database
|                      ----------|----> SERVER: file system
+--------------------------------+
snippetExplanation: What this shows: The host is where the user and the LLM live. Through its clients, it connects out to any number of independent servers, each offering some capability. To the model, the servers' tools appear just like the local tools from Chapter 6 — but behind the scenes, a client relays the request to the right server and brings back the result. Conceptually it resembles how a Spring application consumes a well-defined external service it discovers, except the "consumer" is an LLM-driven agent and the "contract" is a set of tool descriptions.
callout: Host contains clients; each client connects to a server that exposes capabilities. To the model, remote tools look local.

## THEORY
heading: 13.3  What an MCP server offers
body:
An MCP server can expose three kinds of things.

TOOLS: functions the model can CALL — the actions from Chapter 6, now served over the standard protocol. For example: create a ticket, run a query, send a message.

RESOURCES: read-only DATA the host can pull into the model's context — files, records, documents, identified by an address. Think of these as retrievable context sources (closely related to the retrieval ideas of Chapters 10-11).

PROMPTS: reusable prompt templates or canned workflows the server offers, which a user can invoke — a bit like ready-made commands.

Most of your attention goes to TOOLS (the active capabilities), with RESOURCES supplying data. Notice this maps cleanly onto everything you already know: tools are Chapter 6's functions; resources are Chapters 10-11's context sources.
callout: An MCP server exposes tools (Chapter 6's functions), resources (Chapters 10-11's context sources), and prompts.

## THEORY
heading: 13.4  A key point — your agent loop doesn't change
body:
Here is the reassuring part. When an agent uses MCP tools instead of locally-wired tools, the AGENT LOOP from Chapter 7 is unchanged. The only difference is where the tool list comes from and who executes the call.

Before (Chapter 6): the tools were wired directly into your program; your code ran them. With MCP: the client asks the server what tools it offers, and forwards the model's tool requests to the server to run.

The think-act-observe cycle is identical. The model still emits a tool request; something still executes it and returns a result. MCP just standardizes that "something" so tools become pluggable, reusable components rather than code welded into one application. In practice, many hosts in 2026 support MCP out of the box — often you simply POINT the host at a server, and its tools appear to the agent with no code changes at all.
callout: MCP leaves the agent loop unchanged. It just standardizes WHO executes the tool, making tools pluggable and reusable.

## THEORY
heading: 13.5  Why this is a big deal — the ecosystem
body:
Because MCP is a shared standard, a growing MARKETPLACE of ready-made servers exists: for the file system, for source control, for databases, for chat platforms, for cloud services, for web search, and thousands more. This shifts your job in an important way.

REUSE existing servers for common systems instead of rebuilding the same integration everyone else already built. PUBLISH your own server once, and any MCP host can use it. COMPOSE several servers into one agent — weather plus a database plus the file system — mixing and matching capabilities.

Your work moves from "write bespoke glue for each application" toward "assemble capabilities from a standard ecosystem." That is a real productivity and consistency gain, and it is a defining feature of how agents are built in 2026.
callout: Your job shifts from "write bespoke glue" to "assemble capabilities from a standard ecosystem."

## THEORY
heading: 13.6  MCP raises the stakes on security
body:
Connecting an agent to a marketplace of servers is powerful — and, if done carelessly, dangerous. MCP security is an active, serious topic. The main concerns, which build on Chapter 6's safety lessons and preview Chapter 16:

TRUST THE SERVER. An MCP server runs code and can access data and systems. Only connect to servers you trust. Treat a third-party server like an unaudited dependency — a supply-chain risk. Prefer official, first-party servers; review the source of others.

TOOL DESCRIPTIONS AND RESULTS CAN BE WEAPONS. Recall from Chapter 6 that the model is heavily guided by tool descriptions. A malicious server could place manipulative instructions in a tool's description, or hide instructions in the RESULTS it returns, attempting to hijack your agent. (This is a form of "prompt injection," covered fully in Chapter 16.) Treat server-provided text as untrusted.

LEAST PRIVILEGE AND CONSENT. Limit what each server can access. Require user consent for sensitive capabilities, and keep a human in the loop for destructive actions.

AUTHENTICATE REMOTE SERVERS. A server reachable over a network with powerful tools must be properly secured; never expose an unprotected one.

The overarching lesson: MCP does not remove the safety work from Chapter 6 — it EXPANDS it, because now capabilities can come from parties you did not write.
callout: MCP expands the safety work: trust the server, treat its text as untrusted, apply least privilege, authenticate remote servers.

## THEORY
heading: 13.7  When to use MCP, and when not to
body:
USE MCP WHEN: you want tools to be reusable across multiple apps or agents; you want to consume existing ecosystem servers (source control, databases); you are building tools that others will use; or your host or framework already supports it (most do in 2026).

KEEP IT SIMPLE (plain local tools, Chapter 6) WHEN: it is a small, single application and the tool is used nowhere else; you do not need cross-program or cross-vendor reuse; or running a separate server is not worth the overhead.

MCP is about INTEROPERABILITY and REUSE. If you do not need those yet, direct in-program tools are perfectly fine — and you can always wrap them as an MCP server later without changing the underlying logic. This is, once more, the least-complexity principle from Chapter 1.
callout: MCP is about interoperability and reuse. If you don't need those yet, plain local tools are perfectly fine.
