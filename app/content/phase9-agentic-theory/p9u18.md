## THEORY
heading: 18.0  Closing the loop
body:
This is the final chapter, and it closes the loop on your original goal: to understand how to build ANY kind of agentic system, not just one narrow sort. The revelation you will confirm here is that every "type" of agent is the SAME set of ideas from this book — an LLM, tools, a loop, memory, retrieval — arranged with DIFFERENT tools, prompts, and architecture.

Once you truly see that, "any type of agent" stops being intimidating; it becomes a matter of choosing ingredients.
callout: Every agent type is the same ideas — LLM, tools, loop, memory, retrieval — arranged with different ingredients.

## THEORY
heading: 18.1  The universal recipe for any agent
body:
To design ANY agent, answer six questions. Every type in this chapter is just these six answered differently.

1. GOAL — what task or outcome? (This also defines how you'll evaluate it, Chapter 15.)
2. TOOLS — what actions and data does it need? (Chapters 6, 9, 11, 13.)
3. KNOWLEDGE — what must it know? (Put it in the prompt, or retrieve it, or fetch via tools — Chapters 4, 11.)
4. ARCHITECTURE — a workflow or an agent? which pattern? (Chapters 8, 14.)
5. GUARDRAILS — what must it never do; where does a human approve? (Chapter 16.)
6. INTERFACE — how do people invoke it? (Chat, an API, a schedule, an event — Chapter 17.)

Same engine, different car. Keep this list in mind as we tour the types.
callout: Goal, tools, knowledge, architecture, guardrails, interface — six questions design any agent. Same engine, different car.

## THEORY
heading: 18.2  A tour of the major agent types (part 1)
body:
RESEARCH / KNOWLEDGE AGENT (question-answering over your data). The most common real-world agent — "chat with our documents," a support knowledge assistant. It is agentic RAG (Chapter 11): retrieval offered as a tool inside a loop. Signature tools: document search, sometimes web search. Top risk: hallucinating beyond the retrieved context — countered by grounding instructions, citations, and evaluation of retrieval quality.

CODING AGENT. Reads, writes, and runs code to accomplish software tasks. It is a loop (Chapter 7), often with planning and with reflection powered by running tests — an objective critique. Signature tools: read a file, write a file, search code, run tests. Top risk: destructive actions — countered by sandboxing, allowed-command lists, and human approval for anything dangerous.

DATA / ANALYTICS AGENT (talk to your database). Answers questions over structured data by generating and running queries. A loop or a fixed workflow: understand, generate a query, validate it, run it, explain the result. Signature tools: inspect the schema, run a query. Top risk: giving it write access, or query injection — countered by a read-only, least-privilege connection and by validating generated queries.

TASK-AUTOMATION / WORKFLOW AGENT (does things across systems). Performs multi-step actions across tools and APIs — triage a ticket and assign it, onboard a user, process an invoice. Often mostly a WORKFLOW (Chapter 8) with one agentic step, which is safer than full autonomy. Signature tools: the specific system APIs (often reused via MCP servers). Top risk: real side effects — countered by idempotency, human approval for irreversible actions, and least privilege.
callout: Research/Q&A, coding, data/analytics, automation — every one has a core pattern from an earlier chapter.

## THEORY
heading: 18.3  A tour of the major agent types (part 2)
body:
BROWSER / WEB-AUTOMATION AGENT. Operates real websites when there is no API — filling forms, clicking, extracting data. A loop whose "environment" is a browser: it observes the page and takes one action at a time. Signature tools: navigate, click, type, read the page. (Your Playwright familiarity maps here.) Top risks: brittleness (sites change, like flaky UI tests), and indirect prompt injection from page content.

CUSTOMER-FACING / CONVERSATIONAL AGENT (support, sales, tutoring). Converses with end users. Typically routing by intent (Chapter 8), RAG for grounded answers (Chapter 11), tools for actions, and memory across the conversation (Chapter 9). Signature tools: knowledge search, account or order lookups, escalation to a human. Top risks: wrong information and off-brand tone — countered by grounding, output moderation, streaming, and always offering a human handoff.

VOICE / MULTIMODAL AGENT. Interacts by speech or images, not just text. The agent core is unchanged; you add stages: speech-to-text before, text-to-speech after, or a model that accepts images directly. Top risk: latency piling up across the stages (critical for voice) and errors from imperfect speech recognition.

AUTONOMOUS / LONG-RUNNING AGENT. Operates over long periods or on a schedule with little supervision — a monitoring agent, a background worker. Uses planning plus persistent memory so it can pause and resume, with heavy observability and firm global budgets. Top risk (the highest of all): the longer and more autonomous it is, the more can go wrong unsupervised — demanding hard limits, checkpoints, extensive human approval, and vigilant monitoring.

Notice that in every single case, the "core" is a pattern from earlier chapters. THAT is the point of the whole book.
callout: Browser, conversational, voice/multimodal, autonomous — in every case, the core is a pattern you already understand.

## THEORY
heading: 18.5  The whole book on one page
body:
THE FOUNDATION. An LLM is a stateless next-chunk-of-text predictor — fluent, not truthful (Ch 1-2). You manage the conversation; providers are interchangeable (Ch 3). Prompting is a discipline; structured output is the bridge to acting (Ch 4-5).

THE ENGINE. Tools let the model request actions your code performs (Ch 6). An agent is an LLM plus tools plus a loop plus a goal; ReAct is the pattern (Ch 7).

THE STRUCTURE. Choose the least agentic pattern that works (Ch 8). Memory and retrieval give knowledge and recall beyond the finite context (Ch 9-11). Frameworks package the same primitives; MCP standardizes and shares tools (Ch 12-13). Multiple agents are teammates — used only when one agent is not enough (Ch 14).

THE TRUST. Evaluate over datasets; measure, do not guess (Ch 15). Observe everything; guardrails, least privilege, and human approval keep it safe (Ch 16). Ship it: cost, latency, reliability, deployment (Ch 17).

THE APPLICATION. Any agent type is the same primitives with different tools, prompts, and architecture (Ch 18).

If you can reconstruct this map from memory, you understand agentic AI at the level this book set out to give you.
callout: Foundation, engine, structure, trust, application. Reconstruct this map from memory and you understand the field.

## THEORY
heading: 18.6  The three habits that outlast every tool
body:
Frameworks, model names, and provider details will keep changing. Three habits will not, and they are what make someone genuinely good at this.

DECIDE WELL — reach for the least agentic thing that works. Most failures come from unnecessary complexity, not too little.

CONSTRAIN SAFELY — least privilege, guardrails, human approval where it matters. Assume the model can be wrong or fooled, and design so that being wrong cannot cause harm.

MEASURE HONESTLY — evaluate and observe. "It worked once" is not evidence. Let data, not enthusiasm, tell you whether something is good.

Everything else is detail layered on these three.
callout: Decide well, constrain safely, measure honestly — the three habits that outlast every tool.

## THEORY
heading: 18.7  Where to go next
body:
This is a theory book. It gave you the map. The territory — actually building agents — is where understanding becomes skill, and that is exactly what the LevelShift build phases are for. Understand here, build there.

A few pieces of guidance. BUILD SMALL, REAL THINGS — a tiny agent that solves a real annoyance teaches more than any amount of reading; start with the simplest useful one, likely a research/question-answering agent over documents you care about. GO DEEPER ON ONE FRAMEWORK AND ONE DEPLOYMENT PATH — you do not need them all; given your background, Spring AI on the JVM is a natural production home, with a lightweight Python toolkit for prototyping. TREAT EVALUATION AND OBSERVABILITY AS THE REAL SKILL — the differentiator is not "can you make an agent" but "can you make one you can TRUST and keep improving." FOLLOW PRIMARY SOURCES AND RE-DERIVE FROM PRINCIPLES — when a shiny new tool appears, map it onto the one-page model in 18.5.

Your existing strengths are not a starting deficit — they are an edge. Agents are distributed, fallible systems that need clear contracts, tests, resilience, and observability. Those are your instincts already. This book simply added the LLM-specific layer on top of them.
callout: Understand here, build there. Your Java/Spring/QA instincts are an edge, not a gap — agents need contracts, tests, resilience, observability.
